The Challenge: 2TB DynamoDB Schema Evolution & Partition Limits

No DDL rename support, 4-phase rollout strategy, and partition RCU/WCU budget constraints
Part 2: The Challenge
The NoSQL Schema Evolution Protocol

Unlike relational databases with ALTER TABLE RENAME, DynamoDB requires an in-place attribute migration across ~2 TB of live data across 4 distinct deployment phases:

  • Phase 1 Dual-Write Application Code: Read from old attribute, write concurrently to both old & new attributes.
  • Phase 2 Backfill Migration Service (My Focus): Stream historical data, populate new column for rows not yet updated.
  • Phase 3 Cutover Application Code: Read and write exclusively from new column.
  • Phase 4 Cleanup Pass: Run cleanup service to delete legacy column attributes.
Partition Throttle Risks on Live Production
  • RCU Starvation on Direct Reads: Running parallel table scans directly against DynamoDB would exhaust per-partition Read Capacity Units (RCUs), causing immediate read throttling for live enterprise auth queries.
  • WCU Exhaustion on Backfill Writes: High-speed batch updates risk exhausting per-partition Write Capacity Units (WCUs), causing 500 error spikes during live tenant writes.
  • Zero Customer Impact Constraint: Must guarantee zero downtime, zero auth latency degradation, and zero maintenance windows throughout a multi-week migration run.

If we ran the backfill by scanning DynamoDB directly with parallel workers, we would immediately exhaust per-partition RCUs, triggering throttling for live auth queries. The Solution: S3 Streaming Ingestion & Partition Throttling

Zero-RCU S3 snapshots, 1-thread-per-partition worker pool, 5% WCU caps & Datadog observability

1. Point-in-Time Export to S3 (Zero RCU Cost)

Used DynamoDB native S3 export at negligible cost. Reads occurred entirely in S3 with zero RCU consumption on the live table. In-flight updates were safe because application dual-writing was already active.

2. 1-Thread-Per-Partition & Strict 5% WCU Throttling

Knowing that each S3 export file maps to a single partition, we mapped 1 worker thread per partition and strictly capped write throughput to max 5% WCU per thread. Running 50 concurrent threads across hundreds of partitions mathematically guaranteed zero partition throttling.

3. State Persistence in S3 & K8s Restart Recovery

Persisted checkpoints directly in S3 metadata (keeping DynamoDB clean of migration trash). Allowed seamless resumes during K8s pod evictions or node upgrades. Full state & progress telemetry monitored in Datadog.

[7:30 - 11:30] Proud Project - The Solution & Results: - "Here is the solution I engineered: 1. Export to S3: Instead of scanning DynamoDB, we triggered a native DynamoDB point-in-time export to S3. This cost negligible dollars, was significantly faster, and completely eliminated RCU consumption on the live table. In-flight records were safe because the application was already dual-writing. 2. 1-Thread-Per-Partition & 5% WCU Cap: You cannot see per-partition WCU utilization in CloudWatch. So what we did instead is architectural: knowing each S3 export file maps to a single partition, we assigned 1 worker thread per partition and capped write throughput to max 5% WCU per thread. Even running 50 threads in parallel across hundreds of partitions, we mathematically guaranteed we never starved live customer writes. 3. State Persistence in S3: We stored migration checkpoints and offsets directly in S3. This kept DynamoDB completely clean of temporary migration markers, and when Kubernetes evicted pods or upgraded nodes, the workers resumed deterministically from the exact byte offset." - "Results: Migrated ~2TB in a couple of weeks with zero customer impact, tracked everything in Datadog, scaled the service to zero when done, and architected it as a reusable engine for future migrations."

Reflections, Learnings & Hindsight

Architectural validation, operational trade-offs, and what I would do differently
Part 2: Hindsight & Learnings
What Validated the Architectural Choices
  • 5% Per-Thread Partition Capping: Modeling write limits per partition file rather than relying on global table capacity gave mathematical certainty that no individual partition would ever throttle live traffic.
  • S3 Snapshot vs Direct Scan: Exporting to S3 completely insulated our live production table from read pressure, eliminating the need to provision expensive temporary RCUs.
  • S3 Checkpoint Storage: Keeping migration state out of DynamoDB prevented table bloat and schema pollution while making K8s pod restarts effortless.
Considerations & Trade-offs in Hindsight
  • In-Memory Pre-Filtering for Dual-Written Records: For records already updated by Phase 1 application dual-writes during the export window, adding an in-memory check to skip redundant writes earlier would save unnecessary WCU burn.
  • Continuous Hash Sampling Reconciler: Building an automated sampling and hash verification worker to run in parallel with the migration rather than executing post-migration validation checks.
  • Automated Cutover Gates: Automating the parity validation metrics in Datadog to trigger CI/CD deployment pipelines for Phase 3 cutover once backfill reached 100%.
